 1. VISÃO GERAL E ARQUITETURA
================================================================================
 A API centraliza a comunicação entre dois lados:

   [APP ANDROID]                 [BACKEND API]                 [HARDWARE GPS]
   (Kotlin/Compose)              (Node.js + Express)           (ESP32/módulo)
        |                             |                             |
        |-- auth/veículos/rotas ----->|-> Firestore (fonte da verdade)
        |-- comandos block/unblock -->|-> fila de comandos     <---|-- polling
        |<-- telemetria/status --------|<--------------------------|-- telemetria HTTP
        |<-- SSE em tempo real --------|                            |

 - Tecnologias: Node.js >= 22.5, Express 4, firebase-admin (Firestore +
   Realtime Database), SSE para tempo real.
 - NÃO há banco local. O Firestore é o banco único da API; o Realtime Database
   guarda apenas telemetria ao vivo e a última localização de cada celular.
 - Arquitetura: REST simples. Nenhum framework opinativo; camada de middleware
   para auth, serviços para regras de negócio e rotas para HTTP.

 Estrutura de arquivos (backend/src):
   server.js                     - ponto de entrada (liga o processo)
   app.js                        - monta o express (CORS, rotas, logs, painel)
   config.js                     - lê .env e expõe config central
   middleware/auth.js            - requireAuth (ID Token) + requireDevice (headers)
   middleware/error.js           - handlers 404/500 + asyncHandler
   routes/vehicles.routes.js     - CRUD de veículos + device + simulação (app)
   routes/devices.routes.js      - registro do celular do app (mobile_devices)
   routes/telemetry.routes.js    - latest / history / stream (SSE)
   routes/commands.routes.js     - enviar e listar comandos
   routes/routes.routes.js       - start/stop rotas + pontos geográficos
   routes/hardware.routes.js     - endpoints consumidos pelo firmware
   routes/mobile.routes.js       - localização do celular do app (Bearer)
   routes/admin.routes.js        - visão do administrador (painel web)
   services/telemetry.service.js - ingere pontos, atualiza veículo/rota
   services/command.service.js   - fila block/unblock + ACK
   services/simulation.service.js- decide/aplica a simulação (device server-sim)
   services/admin.service.js     - lê Firestore/RTDB e monta os dados do painel
   services/firestore-store.js   - acesso ao Firestore da API
   services/log-buffer.service.js- buffer em memória das requisições (logs)
   realtime/sse.js               - hub Server-Sent Events por veículo
   firebase/firebase-admin.js    - inicializa Admin SDK (sob demanda)
   list-devices.js               - lista rastreadores (Firestore) p/ o api.sh
   hardware-simulator.js         - simula um rastreador em movimento
   util/geo.js                   - haversine (distância entre coordenadas)
   util/road-routes.js           - vias do simulador (rotas viárias)
   util/http-error.js            - classe HttpError (status + mensagem)


================================================================================
 2. DIAGRAMA DE FLUXO DE DADOS
================================================================================
 (A) TELEMETRIA (hardware -> app)
   Hardware POST /v1/hardware/telemetry
        |-> ingestTelemetry()
        |    1. grava ponto em `telemetry` (Firestore)
        |    2. atualiza lat/lng/speed/last_update em `vehicles`
        |    3. se houver rota `em_andamento`, grava em route_points e soma
        |       distância (haversine)
        |    4. publica evento SSE `telemetry` para assinantes do veículo
        |    5. espelha a última posição em RTDB telemetry/{vehicleId}

 (B) COMANDO (app -> hardware -> app)
   App POST /v1/vehicles/:id/commands {command:"block"}
        |-> cria documento `pending` em commands
        |-> SSE `command` (aviso instantâneo no app)
   Hardware GET /v1/hardware/:deviceId/commands?status=pending   (polling)
        |-> recebe o comando, executa no relê
   Hardware POST /v1/hardware/:deviceId/commands/:id/ack {ok:true}
        |-> marca `acknowledged`, seta vehicles.isBlocked
        |-> SSE `blocked` -> app atualiza status na tela
        |-> espelha commands/{vehicleId} no RTDB

 (C) ROTA (app)
   App POST /v1/vehicles/:id/routes/start  -> cria rota `em_andamento`
   Hardware envia telemetria -> pontos acumulam na rota ativa
   App POST /v1/vehicles/:id/routes/stop   -> rota `concluida` (com distância)
   App GET  /v1/routes/:routeId            -> pontos para desenhar a polyline

================================================================================
 4. BANCO DE DADOS (Firebase)
================================================================================
 Não há SQLite. Dois armazenamentos:

 ── Cloud Firestore (instância FIRESTORE_ID, padrão "securitas") ──────────
   users/{uid}
     name, email, phone, firebaseUid, createdAt, updatedAt
     (uid = UID do Firebase Auth; criado/atualizado pela API no requireAuth)

   vehicles/{id}
     id (Number), userId, ownerUid, plate, model, brand, year, color,
     isBlocked, latitude, longitude, speed, lastUpdate, createdAt, updatedAt

   devices/{deviceId}
     deviceId, apiKey, vehicleId, firmware, model, lastSeen, createdAt
     (deviceId = "vt_" + 16 hex; apiKey = 24 bytes hex)
     model = 'server-sim' marca o rastreador VIRTUAL de simulação.

   telemetry/{auto}
     id, vehicleId, deviceId, latitude, longitude, speed, heading, battery,
     timestamp

   routes/{id}
     id, vehicleId, userId, startLatitude/longitude, endLatitude/longitude,
     startTime, endTime, distance, maxSpeed, status
     ('em_andamento'|'concluida'), updatedAt

   route_points/{auto}
     id, routeId, latitude, longitude, speed, heading, timestamp

   commands/{id}
     id, vehicleId, command ('block'|'unblock'), status
     ('pending'|'acknowledged'|'failed'), note, createdAt, acknowledgedAt

   mobile_devices/{uid}
     id, userId, vehicleId, deviceName, createdAt, updatedAt
     (cadastro do CELULAR do app; 1 documento por conta)

 ── Realtime Database (FIREBASE_DATABASE_URL) ─────────────────────────────
   telemetry/{vehicleId}    { latitude, longitude, speed, heading, timestamp }
     -> última posição; o app escuta em FirebaseDataSource.listenTelemetry

   commands/{vehicleId}     { command, timestamp, status }
     -> resposta do comando; o app escuta em listenCommandResponse

   mobile_locations/{uid}   { latitude, longitude, speed, heading, accuracy,
                              timestamp, source }
     -> última posição do celular (POST /v1/mobile/location)


================================================================================
 5. AUTENTICAÇÃO
================================================================================
 APP (usuário)  -> Authorization: Bearer <Firebase ID Token>
   - O LOGIN/REGISTRO é feito pelo Firebase Auth no próprio app Android.
   - A API apenas VALIDA o token (firebase-admin verifyIdToken) no middleware
     requireAuth (src/middleware/auth.js). Não há login nem senha na API.
   - A cada requisição, a API faz upsert de users/{uid} com email/nome/telefone.
   - Middleware: 401 sem token ou token inválido/expirado.

 HARDWARE (dispositivo) -> headers x-device-id + x-api-key
   - Credenciais geradas em POST /v1/vehicles/:id/device.
   - Devem ser gravadas no firmware (flash).
   - Validação: middleware requireDevice (mesmo arquivo), lê devices/{deviceId}
     no Firestore. 401 sem headers, 403 se não casam com devices.

 Códigos de erro do JSON: { "error": "mensagem" }
   400 param inválido | 401 sem auth | 403 sem permissão |
   404 não existe    | 409 conflito  | 500 interno

 6. ENDPOINTS DO APP
================================================================================
 Legenda: 🔒 = exige Authorization: Bearer <Firebase ID Token>

 ── Auth ────────────────────────────────────────────────────────────────────
 (Registro, login e logout acontecem no Firebase Auth: SDK no app Android e
  REST do Identity Toolkit no painel web. A API só valida o ID Token.)

 GET /v1/auth/config
   resp 200: { firebaseApiKey }  (chave pública p/ o login do painel web)

 GET /v1/auth/me  🔒
   resp 200: { user:{ uid, email, name, phone } }

 ── Veículos ────────────────────────────────────────────────────────────────
 GET /v1/vehicles  🔒
   resp 200: { vehicles:[ {id,userId,ownerUid,plate,model,brand,year,color,
                           isBlocked,latitude,longitude,speed,lastUpdate,
                           createdAt} ] }
   Filtra por ownerUid = uid do token (só os veículos do próprio dono).

 POST /v1/vehicles  🔒
   body: { plate, model, brand, year, color? }
   resp 201: { vehicle }
   Placa válida: ABC1D23 (Mercosul) ou ABC-1234 (tradicional).
   409 se placa repetida para o mesmo dono.

 GET /v1/vehicles/:id  🔒
   resp 200: { vehicle, device }

 PUT /v1/vehicles/:id  🔒
   body (parcial): { plate?, model?, brand?, year?, color? }
   resp 200: { vehicle }

 DELETE /v1/vehicles/:id  🔒
   resp 200: { ok:true }

 POST /v1/vehicles/:id/device  🔒
   Gera as credenciais do hardware daquele veículo.
   resp 201: { device:{id,deviceId,apiKey,vehicleId,firmware,model,lastSeen,
                        createdAt} }
   resp 409: já existe device -> { error, device } (idempotente)

 GET /v1/vehicles/:id/simulation  🔒
   resp 200: { simulation:{ simulated, reason, ... } }
   Diz se o veículo está na simulação (rastreador virtual server-sim).

 POST /v1/vehicles/:id/simulation  🔒
   body: { simulate: true|false }
   resp 200: { simulation, vehicle, device }
   Veículo com rastreador real não pode ser simulado.

 ── Telemetria ──────────────────────────────────────────────────────────────
 GET /v1/vehicles/:id/telemetry/latest  🔒
   resp 200: { latest:{id,latitude,longitude,speed,heading,battery,timestamp},
                vehicle:{id,plate,isBlocked,lastUpdate,latitude,longitude,speed} }
   latest = null se o veículo ainda não recebeu telemetria.

 GET /v1/vehicles/:id/telemetry/history?limit=10&after=ts  🔒
   resp 200: { points:[{id,latitude,longitude,speed,heading,battery,timestamp}] }
   limit: 1..500 (padrão 100). after: retorna crescente após o timestamp.

 GET /v1/vehicles/:id/telemetry/stream  🔒  (Server-Sent Events)
   Eventos SSE: telemetry (novo ponto), blocked (estado), command, presence.
   Formato: "event: <nome>\ndata: {...}\n\n"

 ── Comandos (bloqueio/desbloqueio) ─────────────────────────────────────────
 POST /v1/vehicles/:id/commands  🔒
   body: { command:'block'|'unblock', note? }
   resp 201: { command:{id,vehicleId,command,status:'pending',note,createdAt,
                        acknowledgedAt:null} }
   400 se command inválido.

 GET /v1/vehicles/:id/commands?status=pending  🔒
   resp 200: { commands:[...] }  (máx. 100)

 ── Rotas ───────────────────────────────────────────────────────────────────
 POST /v1/vehicles/:id/routes/start  🔒
   resp 201: { route } | resp 200: { route, message:"Rota já em andamento" }

 POST /v1/vehicles/:id/routes/stop  🔒
   resp 200: { route:{...status:'concluida', distance, maxSpeed, endLat,
                      endLng, endTime} }
   404 se não há rota em andamento.

 GET /v1/vehicles/:id/routes  🔒
   resp 200: { routes:[...] } (mais recentes primeiro)

 GET /v1/routes?status=em_andamento  🔒
   rotas de todos os veículos do usuário (filtro opcional por status).

 GET /v1/routes/:routeId  🔒
   resp 200: { route, points:[{id,latitude,longitude,speed,heading,timestamp}] }
   points em ordem cronológica -> usar para desenhar a polyline.

 DELETE /v1/routes/:routeId  🔒
   resp 200: { ok:true }

 ── Localização do celular ──────────────────────────────────────────────────
 POST /v1/mobile/location  🔒
   body: { latitude, longitude, speed?, heading?, accuracy?, timestamp?, source? }
   resp 201: { ok:true, location:{id,userId,latitude,longitude,speed,heading,
                                  accuracy,timestamp,source} }
   400 sem lat/lng ou coordenadas fora de [-90..90]/[-180..180].
   Grava em RTDB mobile_locations/{uid} (estado atual, não histórico).

 GET /v1/mobile/location/latest  🔒
   resp 200: { location:{...} | null }  (última posição do usuário logado)

 ── Registro do dispositivo móvel ───────────────────────────────────────────
 POST /v1/mobile/device  🔒
   body: { deviceName, vehicleId? }
   resp 201/200: { ok:true, device:{id,userId,vehicleId,deviceName,createdAt,
                                    updatedAt} }
   400 sem deviceName; 404 se o veículo informado não pertence ao usuário.
   Grava em mobile_devices/{uid} (1 doc por conta). O app chama no login/
   cadastro/boot com Build.MANUFACTURER + Build.MODEL.

 GET /v1/mobile/device  🔒
   resp 200: { device:{...} | null }

 DELETE /v1/mobile/device  🔒
   resp 200: { ok:true }


================================================================================
 7. ENDPOINTS DO HARDWARE (PROTOCOLO DO FIRMWARE)
================================================================================
 O firmware (ESP32 / módulo GPS) usa APENAS estes 4 endpoints. Autenticação
 via headers em TODAS as chamadas:
   x-device-id: <device_id>     (gerado no POST /v1/vehicles/:id/device)
   x-api-key : <api_key>

 POST /v1/hardware/telemetry
   headers: x-device-id, x-api-key
   body: { latitude, longitude, speed?, heading?, battery?, timestamp? }
   resp 201: { ok:true, vehicleId, pointId, timestamp }
   400 sem lat/lng ou coordenadas fora de [-90..90]/[-180..180].

 GET /v1/hardware/:deviceId/commands?status=pending
   headers: x-device-id, x-api-key
   resp 200: { commands:[{id,vehicleId,command,status,note,createdAt,
                          acknowledgedAt:null}] }
   - Chamar em polling (ex.: a cada 10-15s) ou após cada telemetria.
   - Só retorna comandos 'pending' do veículo vinculado ao device.

 POST /v1/hardware/:deviceId/commands/:commandId/ack
   headers: x-device-id, x-api-key
   body: { ok:true, note? }   (true=executou | false=falhou)
   resp 200: { command:{...status:'acknowledged'|'failed'} }
   - Ao confirmar ok:true de block/unblock, o veículo muda isBlocked
     e o evento SSE `blocked` é disparado.
   - 403 se o comando pertence a outro veículo; 404 se não existe.

 GET /v1/hardware/:deviceId/status
   headers: x-device-id, x-api-key
   usado no BOOT do firmware (valida credenciais).
   resp 200: { deviceId, registered:true,
               vehicle:{id,plate,model,isBlocked} | null,
               pendingCommands: <n>, serverTime }
   resp 403 se credenciais erradas.


================================================================================
 8. TEMPO REAL VIA SSE
================================================================================
 O app abre um GET na stream e o servidor empurra eventos:

   GET /v1/vehicles/:id/telemetry/stream  (Authorization: Bearer)

 event: telemetry   data:{vehicleId,latitude,longitude,speed,heading,battery,timestamp}
   -> disparado a cada ingestão de ponto do hardware.

 event: blocked     data:{vehicleId,isBlocked,command,timestamp}
   -> disparado quando o hardware confirma block/unblock (ACK ok:true).

 event: command     data:{...serialize(command)}
   -> disparado quando um novo comando é criado para o veículo.

 event: presence    data:{connected:true,timestamp,vehicle:{...}}
   -> enviado no momento em que o app assina.

 Implementação: src/realtime/sse.js (hub em memória, 1 Set de conexões por
 vehicleId, heartbeat de 25s). Clientes por process; em multi-process/subir
 vários workers seria necessário um broker (Redis) - fora de escopo do TCC.

 9. PAINEL WEB DO ADMINISTRADOR (/v1/admin)
================================================================================
 O painel web (raiz /, em public/index.html) é HTML+JS puro servido pela API.
 Ele consome as rotas /v1/admin/*, que enxergam QUALQUER veículo de QUALQUER
 usuário (o app continua restrito ao próprio dono via /v1/vehicles). Todas
 exigem Authorization: Bearer (Firebase ID Token).

 Tudo vem DIRETAMENTE do Firestore/RTDB (services/admin.service.js): não há
 mais importação para banco local. O formato das respostas é o mesmo que o
 painel já consumia (counts, users, vehicles, phoneVehicles, screens, service,
 sync), para não mudar o contrato do HTML.

 GET /v1/admin/overview  🔒
   resp 200: { service, counts, sync, users:[...], vehicles:[flattened+owner],
               phoneVehicles, mobileDevices, screens:[...] }
   - service: nome, versão, node, port, dbPath ("Firestore \"securitas\""),
     uptime, pid.
   - counts: users, vehicles, simulatedVehicles, realVehicles, blockedVehicles,
     onlineVehicles, devices, simulatedDevices, realDevices, activeDevices,
     telemetryPoints, routes, activeRoutes, completedRoutes, commands,
     pendingCommands, mobileLocations, recentMobileLocations, mobileDevices,
     phoneVehicles.
   - users: um item por conta (users/ + quem só existe no app), com
     vehicles[], mobileDevice, mobileLocation, realTest, firebaseUid.
   - vehicles: frota inteira achatada (todos os usuários) com `owner` embutido
     — usado pelo mapa para desenhar a frota completa.
   - `simulated` de cada veículo é derivado do device virtual (model='server-sim').
   - sync: estado do Firebase (enabled, credentials, databaseUrl, firestoreId).

 GET /v1/admin/vehicles  🔒
   resp 200: { vehicles:[ serializedVehicle + { owner:{id,name,email} } ] }
   Lista TODOS os veículos de todos os usuários, com o dono e a última
   telemetria. É o que popula o seletor e os marcadores do mapa no painel.

 GET /v1/admin/vehicles/:id  🔒
   resp 200: { vehicle:{...owner}, device:{...}|null, owner:{...},
               telemetry:{último ponto}|null }
   404 se o veículo não existe.

 GET /v1/admin/vehicles/:id/telemetry/latest  🔒
   resp 200: { latest:{...}|null, vehicle:{...}, owner:{...} }

 GET /v1/admin/vehicles/:id/telemetry/history?limit=&after=  🔒
   resp 200: { points:[...] }

 GET /v1/admin/vehicles/:id/telemetry/stream  🔒  (SSE)
   Mesmos eventos do stream do app (`presence`, `telemetry`, `blocked`,
   `command`).

 GET /v1/admin/vehicles/:id/simulation  🔒
   resp 200: { simulation }

 POST /v1/admin/vehicles/:id/simulation  🔒
   body: { simulate: true|false }
   resp 200: { simulation, vehicle, device }

 POST /v1/admin/cloud/import  🔒
   resp 200: { import:{ storage:'firestore', accounts, cloudVehicles, devices,
                        importedAt } }
   Resumo do que existe na nuvem (o Firestore JÁ é o banco da API).

 ── Logs de requisição (buffer em memória) ─────────────────────────────────
 GET /v1/admin/logs?since=&limit=  🔒
   resp 200: { logs:[{seq,method,path,status,durationMs,at}], lastSeq }
   since=<seq> devolve só o que é novo; limit 1..500 (padrão 200).

 GET /v1/admin/logs/stream  🔒  (SSE)
   Stream ao vivo das requisições (mesmo formato do SSE de telemetria).

 GET /v1/admin/log-stats  🔒
   resp 200: estatísticas do buffer (total, últimas janelas etc.)

 10. LIGAÇÃO COM O APP ANDROID
================================================================================
 [1] ApiLinkScreen (config de vínculo)
   - O usuário informa a URL base da API e a apiKey do rastreador
     (x-api-key), gravados localmente (entidade ApiConfig).
   - Hoje o fluxo principal do app usa direto Firebase (FirebaseDataSource)
     e o Firebase Auth; a página serve para as próximas versões.

 [2] FirebaseDataSource.kt (formato que o app LÊ)
   - Firestore: FirebaseFirestore.getInstance(FirebaseApp.getInstance(),
     "securitas") -> coleções users/vehicles/routes com EXATAMENTE os mesmos
     nomes de campos que a API usa (plate, isBlocked, lastUpdate, ownerUid...).
   - O app grava users/{uid} + firebaseUid e vehicles/{id} + ownerUid/
     ownerEmail ao entrar e a cada cadastro/edição/exclusão.
   - RTDB: telemetry/{vehicleId} e commands/{vehicleId} com os mesmos campos
     (latitude, longitude, speed, heading, timestamp / command, timestamp,
     status). O que a API escreve bate com o que o app lê.

 [3] Comando block/unblock pelo app:
   - O app escreve em RTDB commands/{vehicleId} (status pending). O hardware
     físico NÃO lê o RTDB - ele usa a fila HTTP desta API. Para fechar o
     ciclo: app -> POST /v1/vehicles/:id/commands -> hardware polling -> ACK
     -> SSE/RTDB `blocked`.

 [4] Registro do celular:
   - AuthRepository.ensureDeviceRegistered() chama POST /v1/mobile/device no
     login/cadastro e no boot do app (quando já há sessão), enviando
     Build.MANUFACTURER + Build.MODEL. A API grava em mobile_devices/{uid}.

 11. VARIÁVEIS DE AMBIENTE (.env)
================================================================================
 PORT                     porta HTTP (3000)
 SIMULATOR_INTERVAL_MS    intervalo do simulador de hardware (5000)
 SIMULATOR_START_LAT/LNG  partida do simulador (-23.5505 / -46.6333)
 SIMULATION_ENABLED       liga a criação de rastreadores virtuais (true)
 LOG_REQUESTS             log de requisições no console (true)

 FIREBASE_SERVICE_ACCOUNT  caminho do service account JSON (obrigatório)
 FIREBASE_DATABASE_URL     URL do Realtime Database (obrigatório)
 FIRESTORE_ID              nome da instância Firestore ("securitas")

 Obs.: não existem mais DB_PATH, JWT_SECRET nem MAX_TELEMETRY_POINTS — não há
 banco local nem token próprio; a identidade vem do Firebase Auth.

 Regras de segurança (Firebase Rules): valem SÓ para o app Android — o backend
 usa o Admin SDK, que ignora as regras.
   backend/firebase/firestore.rules     -> Firestore (publicar: node scripts/deploy-rules.js)
   backend/firebase/database.rules.json -> Realtime Database (aplicar no Console)

 Acesso do app à API local: o Android bloqueia HTTP em texto claro por padrão.
 O app libera apenas os destinos de desenvolvimento em
   app/src/main/res/xml/network_security_config.xml
 (localhost/127.0.0.1 via `adb reverse tcp:3000 tcp:3000`, 10.0.2.2 do emulador,
 e 192.168.0.10 da rede local). Todo o restante continua exigindo HTTPS.

 13. SIMULAÇÃO DE FROTA E TESTE REAL x SIMULADOR
================================================================================
 Vários veículos podem ser simulados ao mesmo tempo, cada um com seu device.

   Subir a API + um simulador por veículo:
     npm run api

   O ./api.sh lê a frota do FIRESTORE via `node src/list-devices.js` (exclui
   os devices virtuais server-sim), e sobe um processo node por device, cada
   um com PID e log próprios em .run/sim-<n>.pid.

   Variáveis úteis:
     SIM_FLEET=2          limita quantos veículos simular
     START_SIMULATOR=false sobe só a API
     VTSIM_DEVICE_ID / VTSIM_API_KEY  fixa um único veículo

   Cada simulador retoma da posição atual do seu veículo (campo /status),
   então a frota não nasce empilhada em um único ponto.

   Na página inicial (http://localhost:3000), use o seletor de veículos para
   acompanhar cada um. A antiga URL /debug redireciona para a raiz.

 ── Teste real x simulador ────────────────────────────────────────────────
   O Firestore não guarda o flag `simulated` no veículo. A origem é DERIVADA
   do device vinculado:
     device.model = 'server-sim'  -> frota em SIMULAÇÃO
     device.model != 'server-sim' -> veículo de TESTE REAL (criado via
                                     /v1/vehicles, app) ou hardware físico

   O que a página apresenta como "teste real (fora da simulação)":
     - posições do celular recebidas do app (RTDB mobile_locations);
     - veículos sem device virtual;
     - badge "teste real" x "simulador" em cada veículo da lista;
     - marcador azul do celular junto do veículo quando o proprietário já
       enviou a posição pelo app (legenda "Celular (teste real)").

   O overview (/v1/admin/overview) expõe counts.simulatedVehicles,
   counts.realVehicles, counts.simulatedDevices, counts.realDevices e, por
   usuário, vehicles[].simulated e user.realTest.

   Visão do administrador x visão do app:
     - O app usa /v1/vehicles*, restrito ao veículo do próprio dono.
     - O painel web usa /v1/admin/vehicles*, que enxerga qualquer veículo de
       qualquer usuário (a frota inteira), com o dono identificado.
